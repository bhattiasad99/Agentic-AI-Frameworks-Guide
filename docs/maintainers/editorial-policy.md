# Editorial and Source Policy

## Inclusion criteria

A framework should be included only when it:

1. addresses a meaningful part of the AI software-development lifecycle;
2. is publicly usable and has an accessible source repository;
3. provides enough first-party documentation to verify a starter workflow;
4. differs materially from existing entries;
5. has clear reader benefit beyond novelty or popularity.

## Source hierarchy

Use sources in this order:

1. Current official documentation
2. Upstream repository README and release notes
3. Upstream source/configuration when documentation is incomplete
4. Maintainer discussions and issues for known limitations
5. Independent hands-on reports for experience—not installation authority

Never source an exact command from an SEO comparison article when upstream documentation exists.

## Claim types

- **Fact:** Directly supported by an upstream source.
- **Observation:** Visible repository or workflow characteristic.
- **Inference:** A reasoned conclusion; label it.
- **Recommendation:** Editorial judgment based on stated trade-offs.

## Maintenance

- Recheck high-change starter guides regularly.
- Update the checked date only after reviewing upstream instructions.
- Prefer correcting a command over preserving backward compatibility in prose.
- Note beta, deprecated, migrated, archived, or gated workflows prominently.
- Remove abandoned entries when they no longer provide safe learning value; preserve the decision in Git history.

## Independence

Contributors must disclose employment, sponsorship, ownership, or another material affiliation with a framework they add or promote. Affiliation does not disqualify a contribution; undisclosed promotion does.

## Writing style

- Lead with the problem solved.
- Use short paragraphs, useful tables, and concrete examples.
- Explain acronyms on first use.
- Include “do not use when” guidance.
- Avoid unsupported productivity multipliers.
- Do not rank by stars.
