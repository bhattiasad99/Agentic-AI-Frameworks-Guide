# Contributing

Thank you for helping developers make better decisions about AI-driven development.

## What belongs here

Good contributions provide at least one of these:

- a verified correction to installation or first-use instructions;
- a concrete trade-off missing from a framework guide;
- a reproducible workflow, measurement, or production lesson;
- a genuinely distinct framework that fills an uncovered category;
- clearer teaching, navigation, accessibility, or examples.

This repository is curated. Popularity alone does not qualify a project.

## Before adding a framework

Open a framework proposal issue and answer:

1. Which recurring development failure does it solve?
2. How is it materially different from existing entries?
3. Is it open source, documented, and usable today?
4. What is the smallest verified starter workflow?
5. When should a developer not use it?
6. Which first-party sources support the claims?
7. Who tested the instructions, on which tool and operating system?

## Editorial requirements

- Prefer first-party repositories, documentation, and release notes.
- Link directly to supporting material.
- State upstream instructions as instructions; label personal judgment clearly.
- Do not copy upstream marketing copy.
- Do not use star counts as a proxy for engineering quality.
- Include risks, limitations, maturity, and maintenance signals.
- Use exact commands only when verified against current upstream material.
- Add or update the `Upstream checked` date.
- Keep sentences direct, useful, and free of keyword stuffing.

See the full [editorial and source policy](docs/maintainers/editorial-policy.md).

## Pull request workflow

1. Fork the repository and create a focused branch.
2. Make one coherent contribution.
3. Check headings and relative links.
4. Verify every changed external URL.
5. Preview Markdown on GitHub or a compatible renderer.
6. Complete the pull request checklist with sources and test details.

## Starter guide shape

Framework pages should normally contain:

```md
# Framework Starter Guide

**Category:**
**Best for:**
**Upstream:**
**Upstream checked:** YYYY-MM-DD

## What it changes
## Use it when
## Start a project
## First exercise
## Production checklist
## Sources
```

## Commit and PR style

Use a short imperative or descriptive title, for example:

- `Correct OpenSpec Cursor command names`
- `Add Windows notes to GSD starter`
- `Document autonomous-loop test weakening risk`

## Community conduct

Be precise without being hostile. Critique workflows and claims, not contributors. Disclose affiliations with a framework or vendor.
